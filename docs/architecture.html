Pocket Queue / Documentation / Architecture
Flutter implementation

Small layers, fast feedback.

Pocket Queue uses a deliberately compact architecture for an offline MVP: a single observable store, explicit queue transitions, reusable UI components, and platform services only where they improve the operator workflow.

Layer overview

Presentation

Material 3 widgets, responsive layout helpers, reusable cards, status pills, empty states, settings sections, and navigation.

State and domain

QueueStore owns business settings, queue settings, queue entries, sorting, transitions, statistics, CSV serialization, and reset behavior.

Persistence

SharedPreferences stores scalar settings and JSON-encoded queue records. The app does not depend on a backend.

Platform services

share_plus opens the native or web sharing flow for CSV export. Flutter's platform targets provide the Android host and browser verification target.

State flow

Widget action
    ↓
QueueStore transition
    ├── validate current state
    ├── mutate QueueEntry or setting
    ├── persist JSON/settings locally
    └── notifyListeners()
    ↓
AnimatedBuilder rebuilds app surface
    ↓
Queue, display, history, statistics, and settings stay consistent

Responsive navigation

On compact screens, MainShell uses a Material NavigationBar with Queue, Display, History, and Settings. At 860 pixels or wider, it switches to a NavigationRail, leaving more room for the operational surface. The queue screen also switches from stacked cards to a two-column current/next layout at 760 pixels.

Reliability decisions

DecisionWhy it matters
Central storePrevents queue state from drifting between Queue, Display, History, and Statistics.
Explicit transitionsCall Next, Finish, Skip, and Recall have one source of truth and cannot accidentally create duplicate active tickets.
Confirmation dialogsReset and delete operations are destructive and require a deliberate operator decision.
Large touch targetsOperational actions remain usable on small phones and busy service desks.
Local persistenceCore queue operations continue without an internet connection and survive a restart.

Testing strategy

The automated suite checks onboarding visibility and queue behavior. The queue tests verify the algorithmic contract: regular numbering, priority ordering, call-next, recall count, finish transition, reset behavior, and skipped history count. The GitHub workflow runs analysis, tests, and a debug APK build for every change.
